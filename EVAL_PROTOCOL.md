# Evaluation Protocol

**Written and committed:** 2026-11-20, **before** any data was generated or any result produced.
**Rule for changes:** this text is frozen. Any later change goes in the *Amendments* section at the bottom as a dated note, with the reason. Results produced under earlier versions stay in `evidence/eval_results.md` and are never deleted or overwritten.

---

## 1. Question

Does the explainable decline-anomaly method (D7) find real **acceptance failures** on migrated cards better than a simple dashboard-style rule? Does it do so **without** flagging legitimate issuer declines? And are its GenAI explanations grounded in the data?

## 2. Data

- Synthetic only, generated by `tools/gen_data.py` with a **fixed seed**, recorded in the results.
- 60 days of authorizations. The generator writes an **incident manifest** (`evidence/incident_manifest.json`) giving each planted incident's ID, affected slice (acquirer / channel / MCC group / region / wave), start and end hour, and type. **The method under test never reads the manifest.** Only the evaluation script reads it.

| Split | Days | Planted incidents | Use |
|---|---|---|---|
| Tuning | 1–40 | #1 ACQ-017 e-commerce token misconfiguration; #2 international block, one MCC group | Choose the method's score threshold and minimum-volume floor |
| **Held out** | **41–60** | **#3 recurring charges failing after reissue; #4 regional processor timeouts; DECOY: holiday spike in legitimate insufficient-funds declines** | Report results; never used for tuning |

## 3. Methods compared

| | Definition | Tuning |
|---|---|---|
| **Baseline** | Flag an (hour, acquirer) slice when its decline rate > **1.5×** its own trailing 7-day average decline rate. Roughly what dashboards do today. | None; the 1.5× is fixed in advance |
| **Method** | Per (hour, wave cohort, acquirer × channel × MCC group × region) slice: a z-score of the decline-rate excess over the **matched baseline**, restricted to *acceptance* standard categories, plus root-cause attribution by category concentration (D7) | Threshold and volume floor chosen on days 1–40 only to maximize incident recall at ≥ 80% precision, then **frozen and recorded** before the held-out days are scored |

## 4. Timing rule (no look-ahead)

- Each window is scored using only events with event time ≤ the end of that window **and** a load time ≤ the scoring time.
- A late legacy file contributes only from its `_load_ts` onwards, never retroactively.
- The baseline and matched-baseline statistics use **prior windows only**.
- The SCD2 card attributes are taken as of the event time: a card's wave is the one it was in *at that moment*.
- The evaluation replays the held-out days in time order, so it simulates live scoring rather than one batch over all data.

## 5. Measures

**Main measure: held-out incident recall at ≥ 80% precision.**
- An incident is **caught** if at least one flagged slice-window overlaps its manifest slice and time range.
- **Precision** = flagged slice-windows that overlap a planted incident ÷ all flagged slice-windows, on the held-out days.

**Secondary:**
1. **Median detection delay:** first flag minus incident start, in hours of event time. The replay latency (file landed → anomaly in `gold_anomalies`) is reported separately in minutes.
2. **Slice-window recall and precision** over all affected slice-windows. This is reported because there are only 2 held-out incidents, so the incident-level recall can only be 0%, 50% or 100%.
3. **Decoy result:** whether any slice-window in the decoy is flagged with an *acceptance* root cause.
4. **Root-cause accuracy:** the share of caught incidents whose attributed cause matches the manifest type.

**GenAI explanations (D8)**
- 30 explanations from held-out anomalies, sampled at random with a fixed seed. If there are fewer than 30, all of them.
- Each is graded by an MLflow LLM judge on three pass/fail criteria:
  - (a) **Grounded:** every number cited matches the source row.
  - (b) **Cause agreement:** the stated cause matches the attributed root cause.
  - (c) **Actionable:** it names an owner team and a concrete next step.
- (a) is also checked **by rule**: numbers are extracted and compared with the row. The rule check wins if the two disagree.

## 6. What would mean "no claim"

| Result | Consequence |
|---|---|
| The method's held-out recall is not at least **20 points** higher than the baseline's, at equal or better precision | No claim that the method beats today's approach |
| The method flags the **decoy** with an acceptance cause | No claim that it separates acceptance failures from legitimate declines; this is reported as a failure |
| Precision is < 50% at any threshold that catches an incident | No claim of operational usefulness (too many false alarms) |
| Grounding (a) is < 90% by the rule check | No claim about explanation quality; explanations shown as illustrative only |
| Any evidence of look-ahead (the timing rule broken) | All results void until re-run |

**Small-sample caveat (stated in advance):** with two held-out incidents, any result is indicative, not statistically significant. The deck and README must say so.

## 7. Reporting

`src/ai/evaluate.py` writes `evidence/eval_results.md`, containing:
- the date, protocol version, generator seed and frozen threshold;
- a table of every measure, for both the baseline and the method;
- the decoy result and the per-incident detail;
- the judge scores, plus each no-claim condition checked.

The run also ends with a JSON summary.

### Amendment 2: 2026-11-23 (before any detection result was produced)
Approved by the submitter. No score, flag or evaluation result existed when this was written.
1. **Grain: one day for both methods.** The method scores (business day × slice); the baseline scores (business day × acquirer) with the same rule as §3 (decline rate > 1.5× the acquirer's own trailing 7-day average daily decline rate; all declines, both networks). The detection delay in §5 is measured in whole days.
   *Reason:* at prototype scale (1:270) hourly slices hold 1–3 transactions (the hourly × 9-dimension gold table was 7.9M rows for 10.9M attempts), and the daily grain was already approved for gold (DECISIONS.md 2026-11-21).
2. **Expected rate.** The "matched baseline" in §3 is, for each acquired-network (Meridian) slice, **that slice's own acceptance-failure rate over the prior 28 days**, shrunk toward the network-wide prior-28-day rate with a pseudo-count of 500 attempts. Prior windows only. The legacy network cannot serve as the reference for acceptance failures, because it has almost none (about 0.05%); comparing against it would flag every Meridian slice every day. The legacy-matched baseline stays in `gold_baseline_gap` (approval-rate gap) and is not used for detection.
3. **"Overlaps an incident" (precision, §5).** A flagged slice-day counts as a hit for incident *k* when planted rows of *k* make up **≥ 50% of that slice-day's excess declines**. For the method, the excess is acceptance declines minus expected. For the baseline, it is all declines minus the trailing average × attempts. Otherwise it is a false positive. Decoy rows are never incident rows, so a flag driven by the decoy is a false positive for both methods.
4. **Unchanged:** the split (tuning = window days 1–40, held out = days 41–60), the timing rule (each day D is scored at **D+1 07:00**, using only rows whose source files had landed by then), the main measure, the secondary measures and the no-claim conditions. Results produced under this amendment are labelled "protocol v1 + A1 + A2".
